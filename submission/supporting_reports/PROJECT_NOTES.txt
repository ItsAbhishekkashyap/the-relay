SECTION 1: PROJECT OVERVIEW
================================================================================

1.1 What is "The Relay" Assignment?
------------------------------------
"The Relay" is a machine learning engineering project designed by Vaani
Research. The assignment requires building a production-grade, highly reliable,
and verifiable Research Assistant.

The assistant is strictly constrained to answer technical questions from three
specific arXiv research papers:
1. arXiv:1706.03762v7 - "Attention Is All You Need" (The Transformer paper)
2. arXiv:2410.00037v1 - "Moshi: A Speech-Text Foundation Model for Real-Time
   Dialogue"
3. arXiv:2507.07955v2 - "Dynamic Chunking for End-to-End Hierarchical Sequence
   Modeling"

1.2 The Problem We Are Solving
------------------------------
Standard Large Language Model (LLM) applications face severe real-world problems:
1. Hallucination: Models invent plausible-sounding facts, equations, and page
   numbers when they do not know the answer.
2. Lack of Traceability: General chat assistants cannot point to the exact
   table, page, or paragraph that proves their statement.
3. Fragile Rate Limits: Cloud model providers (like Groq, OpenAI, or Anthropic)
   strictly limit Requests Per Minute (RPM), Tokens Per Minute (TPM), and daily
   call volumes. Uncontrolled bursts crash applications with HTTP 429 errors.
4. Upstream Latency and Outages: Network dropouts, transient 5xx errors, and
   slow token generation degrade user experience unless handled by an
   intelligent traffic management layer.

1.3 What the Complete System Will Do
------------------------------------
When fully assembled, the system will:
- Ingest the original research PDFs with 100% text and table fidelity.
- Search for evidence across three complementary retrieval channels:
  * Dense semantic embeddings (understanding concepts and paraphrases).
  * Sparse BM25 keyword matching (finding exact names, numbers, and formulas).
  * Structured SQLite tables (retrieving raw tables, metrics, and exact facts).
- Fuse search results using Reciprocal Rank Fusion (RRF) with exact citations.
- Route user requests through an asynchronous Traffic Manager that enforces
  queuing, deadlines, concurrency ceilings, local rate admission, and retries.
- Pass prompts to either a real high-speed cloud provider (Groq) or a local
  mock simulator (FastAPI stand-in) that replicates latency and rate limits.
- Orchestrate the multi-step reasoning flow using a stateful LangGraph agent
  (to be implemented in Stage 3C).

1.4 Core Technologies and Why We Chose Them
-------------------------------------------
- Python 3.12: Modern, robust async/await syntax, strong typing, and performance.
- uv (by Astral): Extremely fast Rust-based Python package and virtualenv manager.
- PyMuPDF (fitz): High-speed, zero-dependency PDF text and table extraction.
- LangChain: Standard document representation and recursive text chunking.
- Sentence Transformers: Local dense vector embeddings (all-MiniLM-L6-v2) that run
  efficiently on CPU without external API costs or rate limits.
- ChromaDB: Lightweight, embeddable, persistent vector database.
- rank-bm25: Fast in-memory probabilistic keyword retrieval algorithm.
- SQLite3 & FTS5: Built-in, zero-dependency SQL database with full-text search
  for structured tables and numerical facts.
- FastAPI & Uvicorn: Modern asynchronous web framework powering the stand-in
  simulator.
- Groq Python SDK: Ultra-fast LPU cloud inference engine for production calls.
- Pydantic v2: Strict data validation and settings management across schemas.
- pytest & anyio: Comprehensive asynchronous test automation framework.

1.5 High-Level Architecture Explained Simply
--------------------------------------------
Think of the system like a research library with a security desk:
1. The Books: The three research papers stored as PDF files.
2. The Index Cards: PyMuPDF and LangChain break the books into smaller,
   labeled index cards (chunks) with page numbers and section headers.
3. The Search System (Hybrid Retrieval):
   - The Semantic Librarian (ChromaDB) finds ideas that mean the same thing.
   - The Keyword Catalog (BM25) finds exact words and acronyms like "d_model".
   - The Fact Ledger (SQLite) looks up exact numbers and markdown tables.
   - The Fusion Judge (RRF) combines all three lists and picks the best cards.
4. The Dispatcher (Traffic Manager): A smart gatekeeper that organizes questions
   in a line (FIFO queue), ensures no more than 5 questions run at once,
   prevents exceeding rate limits, and retries if an answer dropped.
5. The Answering Machine: Groq (real AI) or the Simulator (local training AI).

---------------------------------------
Contains all document processing, chunking algorithms, and retrieval engines:

3.3 Stage 2.2: Chunking Strategy Prototype
------------------------------------------
Goal: Understand how splitting text affects retrieval quality.
- What is Chunking? Large Language Models cannot ingest an entire 66-page paper
  in a single retrieval query without high cost, latency, and "lost in the middle"
  degradation. Chunking divides long text into small, self-contained paragraphs.
- Evaluated three early prototypes:
  1. Fixed-Size Chunking: Splits strictly by character count with a fixed overlap.
     Limitation: Cuts words and sentences in half.
  2. Sentence-Aware Chunking: Splits along sentence boundaries (`. `, `? `, `! `).
     Limitation: Ignores headings and mixes unrelated sections.
  3. Structure-Aware Chunking: Splits along detected headings.
     Limitation: Headings vary wildly across paper formats and require specialized
     token counting.
- Key Learning: We needed a production-ready splitter that counts actual model
  tokens (not characters) and preserves section metadata.

3.4 Stage 2.2A: Docling vs. PyMuPDF Benchmark Evaluation
--------------------------------------------------------
Goal: Evaluate whether IBM's Docling deep-learning PDF parser produces superior
results compared to PyMuPDF.
- Setup: Created an isolated virtual environment (`.venv_docling`) and benchmarked
  both tools on representative pages (tables, multi-column text, formulas).
- Benchmark Findings:
  * Speed: PyMuPDF processed the papers in ~0.5 seconds. Docling required
    over 3 minutes (hundreds of times slower) due to heavy deep-learning models.
  * Memory/Disk: Docling required gigabytes of PyTorch dependencies and heavy
    RAM usage. PyMuPDF required only a few megabytes.
  * Table Quality: While Docling extracted clean markdown tables, PyMuPDF's
    built-in table extraction feature was also able to extract clean tabular
    Markdown when configured properly.
- Decision: We rejected Docling for the main pipeline to maintain a lightweight,
  ultra-fast, CPU-friendly system. PyMuPDF was confirmed as the official extractor.

3.6 Stage 2.3B: LangChain PDF Ingestion and Token-Aware Chunking
----------------------------------------------------------------
Goal: Convert raw PDFs into production-grade token-bounded LangChain chunks.
- Document Ingestion (`app/retrieval/pdf_ingestion.py`):
  * Reads pages using PyMuPDF block dictionaries.
  * Detects headings using font size and capitalization rules.
  * Critical Fix: When a heading is encountered, the current prose group is
    immediately flushed. The heading introduces a new section, ensuring prose
    blocks never inherit the wrong section name across page boundaries.
  * Tables are converted into verbatim Markdown tables with explicit page numbers.
- Token-Aware Splitting (`app/retrieval/langchain_chunking.py`):
  * Utilizes `RecursiveCharacterTextSplitter` configured with the Hugging Face
    tokenizer for `sentence-transformers/all-MiniLM-L6-v2`.
  * Chunk Size: 512 tokens maximum.
  * Chunk Overlap: 76 tokens (~15% overlap) to prevent losing context across cuts.
  * Output: Ingested 265 clean LangChain Documents and produced exactly 402
    chunks across all three papers (50 + 203 + 149 chunks).
  * Saved to `data/chunks/langchain_recursive/` and documented in
    `reports/langchain_chunking_report.json`.

3.7 Stage 2.4: Hybrid Multi-Modal Retrieval Engine
--------------------------------------------------
Goal: Implement an evidence-based retrieval engine combining three search channels.
- Why Not Just Vector Search? Vector embeddings understand semantic similarity
  (e.g., "fast dialogue" matches "real-time speech"), but they fail on exact
  acronyms (e.g., "d_model"), specific version numbers, or numbers in tables.
- Channel 1: Dense Vector Retrieval (`DenseRetriever`):
  * Uses Sentence Transformers (`all-MiniLM-L6-v2`) generating 384-dimensional
    dense vectors stored persistently in ChromaDB.
  * Queries using cosine distance over semantic concepts.
- Channel 2: Keyword Retrieval (`BM25Retriever`):
  * Tokenizes chunks while preserving technical terms (e.g., `1706.03762v7`).
  * Scores documents based on Term Frequency and Inverse Document Frequency (TF-IDF).
- Channel 3: Structured Fact Store (`FactStore`):
  * Stores tabular elements, formulas, and numeric metrics in SQLite (`fact_store.db`).
  * Features SQLite FTS5 for full-text search and exact substring matching on numbers.
- Reciprocal Rank Fusion (RRF):
  * Combines ranked results from all three channels using the formula:
    RRF_Score(d) = SUM_{channel} [ 1 / (60 + rank(d)) ]
  * Chunks returned by multiple channels naturally float to the top.
  * Returns complete provenance: paper title, arXiv ID, page number, section,
    and exact chunk text.
  * Channel failures are explicitly tracked and exposed in diagnostic metadata.

3.8 Stage 3A: Real Groq Provider and Local Stand-in Model Simulator
-------------------------------------------------------------------
Goal: Provide swappable model backends behind a unified provider interface.
- Common Interface (`app/providers/base.py`):
  * `generate(request) -> GenerationResponse`
  * `stream(request) -> AsyncIterator[StreamChunk]`
- Real Groq Provider (`app/providers/groq_provider.py`):
  * Connects to Groq Cloud API for ultra-fast LPU inference.
  * Captures streaming token usage from trailing SDK chunks (`stream_options`).
  * Correctly sets `time_to_first_token=None` for non-streaming calls.
- Stand-in Model Simulator (`simulator/service.py` & `simulator/main.py`):
  * A full local FastAPI server replicating an LLM provider on port 8001.
  * Simulates network latency (base delay + random jitter).
  * Local Rate Limiting: RPM (Requests Per Minute), TPM (Tokens Per Minute),
    and daily request budgets using sliding 60-second windows.
  * Conservative TPM Reservation: Reserves prompt tokens plus an output allowance
    at admission to prevent concurrent requests from collectively breaching limits.
  * Lifecycle Safety: Handles task cancellation (`asyncio.CancelledError`) and
    early stream termination (`GeneratorExit`) without leaking reservations.

3.9 Stage 3B: Asynchronous Traffic Manager and Concurrency Controller
---------------------------------------------------------------------
Goal: Protect model providers from traffic overload, burst spikes, and timeouts.
- Bounded FIFO Queue: Requests enter a strictly ordered First-In, First-Out
  queue. If queue depth exceeds `max_queue_size`, new requests are immediately
  rejected with `QueueFullError` rather than consuming infinite memory.
- Concurrency Control: Enforces a hard ceiling (`max_concurrency`) on the
  number of simultaneous requests executing with the provider.
- Local Rate Admission: Tracks RPM, TPM, and UTC daily request budgets.
  Rejects excess requests with `LocalRateLimitError` (HTTP 429) carrying `retry_after`.
- End-to-End Deadlines:
  * Measures total time spent (queue wait time + provider execution time).
  * If a request expires in the queue, it raises `QueueTimeoutError` and the
    provider is **never called**.
  * If a request expires during execution, it cancels the provider call and
    raises `ExecutionTimeoutError`.
- Centralized Bounded Retries:
  * Automatically retries transient errors (500, 502, 503, 429, timeouts).
  * Never retries non-transient errors (401 Unauthorized, 400 Invalid Request).
  * Uses exponential backoff with random jitter or respects `retry_after`.
  * Aborts retries if the backoff delay would exceed the request deadline.
- Incremental Streaming & Non-Restart Rule:
  * Yields chunks immediately as they arrive over HTTP.
  * If an error occurs before any content text has been emitted (e.g. empty or
    metadata chunk), the stream can be retried.
  * Once non-empty text has been delivered to the user, transparent restarts are
    strictly disabled (raises `StreamAlreadyStartedError`) to prevent duplicate text.
- Cancellation-Safe Settlement:
  * Implemented `_settle_request()` protected by task uncancel/cancel logic.
  * Guarantees that cancellation while waiting for a lock cannot leak in-flight
    slots or active token reservations.

4.2 Step-by-Step Data Flow
--------------------------
1. Offline Indexing:
   - Source PDFs are read from `papers/` by PyMuPDF.
   - Text, headings, and tables are converted to LangChain Documents.
   - Token-aware chunking creates 402 chunks saved in `data/chunks/langchain_recursive/`.
   - `build_retrieval_index.py` builds the vector index (`chroma.sqlite3`),
     the keyword index (`bm25_index.json`), and the fact database (`fact_store.db`).
2. Online Retrieval:
   - A question arrives at `HybridRetriever`.
   - The question is dispatched concurrently across Dense, BM25, and FactStore channels.
   - Channel rankings are fused using RRF. Chunks supported by multiple channels
     receive higher scores.
3. Traffic Management & Generation:
   - Application code formats a prompt with retrieved context and calls
     `traffic_manager.execute(request)` or `traffic_manager.stream(request)`.
   - TrafficManager verifies queue capacity. If full, it rejects immediately.
   - Request waits in FIFO order until concurrency slot and rate limits permit admission.
   - TrafficManager passes the request to the configured model provider (Groq or Simulator).
   - If an error occurs, TrafficManager manages retries or cleanly rolls back reservations.

SECTION 5: IMPORTANT TECHNICAL DECISIONS & TRADE-OFFS
================================================================================

5.1 What We Chose and Why
-------------------------
1. Python 3.12 and FastAPI:
   - Python is the standard language of modern AI/ML engineering.
   - Python 3.12 provides improved asyncio exception groups, task cancellation
     protections, and faster runtime execution.
   - FastAPI provides high-speed, asynchronous HTTP handling with native Pydantic
     validation for the model simulator.

2. PyMuPDF Instead of Docling:
   - PyMuPDF processes all three papers in ~0.5 seconds on CPU with virtually zero
     disk overhead.
   - Docling required 3+ minutes, gigabytes of deep-learning weights (PyTorch/Transformers),
     and high RAM usage.
   - PyMuPDF provided all the structural block coordinates and table extraction
     needed without third-party heavy weight models.

3. LangChain for Documents and Splitting:
   - Provides standardized `Document(page_content, metadata)` representations.
   - `RecursiveCharacterTextSplitter` respects natural text separators (`\n\n`, `\n`, ` `)
     while adhering to exact token count ceilings.

4. Sentence Transformers (`all-MiniLM-L6-v2`) for Local Embeddings:
   - Runs locally on CPU in milliseconds.
   - Generates compact 384-dimensional dense vectors.
   - Eliminates dependence on external embedding APIs, costs, and rate limits.

5. ChromaDB for Vector Storage:
   - Runs in-process (embedded) without requiring Docker, external databases,
     or cloud setup.
   - Stores vectors and metadata persistently in SQLite.

6. BM25 for Keyword Search:
   - Essential for finding exact technical terms (e.g. `d_model`, `BLEU`, `RQ-Transformer`)
     and arXiv version identifiers that dense vector embeddings blur together.

7. SQLite with FTS5 for Structured Facts:
   - Tables and formulas contain exact numerical data (e.g. "28.4 BLEU", "160ms latency").
   - Storing raw markdown tables in SQLite enables exact substring lookups and
     full-text searching without embedding distortion.

8. Hybrid Retrieval with Reciprocal Rank Fusion (RRF):
   - Rather than guessing arbitrary weight multipliers (e.g. 0.7 dense + 0.3 keyword),
     RRF evaluates rank position across all active search channels.
   - Chunks discovered by multiple retrieval methods naturally achieve the highest
     relevance rank.

9. Groq as the Real Model Provider:
   - Groq LPUs provide extremely low inference latency (hundreds of tokens per second),
     enabling fast real-time user experiences and quick automated evaluations.

10. Stand-in FastAPI Simulator:
    - Allows developing and testing the entire system offline without paying for
      cloud API tokens or risking Groq account rate limits.
    - Deterministically tests rate limiting (RPM/TPM), daily budget exhaustion,
      and network errors.

11. Asyncio-Based Traffic Management:
    - Pure Python asynchronous concurrency control using queues, events, and locks.
    - Zero external messaging broker dependencies.

5.2 What We Deliberately Avoided
--------------------------------
- Avoided Heavy External Infrastructure: No Redis, Celery, RabbitMQ, Kafka, or
  Postgres. Pure Python asyncio and SQLite provide lightweight, portable code
  that runs on any developer laptop.
- Avoided Cloud Embedding APIs: Using OpenAI or Cohere embedding APIs would introduce
  network latency, cost, and additional rate limits during testing.
- Avoided Docling in Production: Prevented adding gigabytes of PyTorch bloat and
  multi-minute parsing delays to the extraction pipeline.

SECTION 9: KNOWN LIMITATIONS AND OPERATIONAL ASSUMPTIONS
================================================================================

9.1 Known Limitations
---------------------
1. Local Admission vs. Remote Groq Limits:
   The configured local RPM, TPM, and daily budget limits enforce local traffic
   shaping and concurrency protection. They do not clone or communicate with
   Groq's internal proprietary account tier counters.
2. Ambiguous Network Retries:
   If an HTTP connection drops after a request reaches the remote server but before
   the response is received, retrying may cause duplicate execution on the provider.
   Distributed systems cannot guarantee exactly-once delivery across broken connections.
3. In-Memory Simulator State:
   The FastAPI model simulator tracks active sliding-window reservations in memory.
   Restarting the simulator server resets its live usage counters.
4. CPU Embedding Speed:
   Local embeddings (`all-MiniLM-L6-v2`) run on CPU. While extremely fast for
   single queries (~20ms), generating thousands of embeddings during index
   creation takes a few minutes.

9.2 Operational Assumptions
---------------------------
1. Three Papers Only:
   The system assumes questions are strictly answered from the three provided
   arXiv papers. Out-of-domain general knowledge questions must be refused.
2. Tokenizer Heuristic:
   TrafficManager token admission estimates prompt tokens using an approximation
   (~1.33 tokens per word). Actual token counts returned by the provider on
   completion reconcile the reservation.

9.3 Deprecation Warnings and Rules of Thumb
-------------------------------------------
- PyMuPDF Warning: You may see `FutureWarning: The fitz API is deprecated and
  will be removed in future. Use import pymupdf instead.` This warning is harmless
  and does not affect functionality.
- Do Not Modify Chunking or Ingestion: The 402 generated chunks and their
  corresponding ChromaDB, BM25, and SQLite indexes are approved artifacts.
  Do not re-index or alter chunk IDs without an explicit architectural requirement.
